# Business Intelligence

## تمرین اول: استخراج داده و شبیه‌سازی سیستم OLTP (پلتفرم اسنپ اکسپرس)

### شرح پروژه
هدف این تمرین، جمع‌آوری داده‌های واقعی از پلتفرم اسنپ‌اکسپرس (Snapp Express) و شبیه‌سازی یک سیستم پردازش تراکنش‌های آنلاین (OLTP) جهت تامین داده‌های اولیه برای پایپ‌لاین هوش تجاری است. ساختار پروژه بر اساس معماری چند-فروشگاهی (Multi-vendor) پیاده‌سازی شده و محدودیت‌های عملکردی (نظیر Rate Limiting و سربار محاسباتی) در آن بهینه‌سازی شده‌اند.

### ساختار ماژول‌ها
کد منبع این فاز به سه اسکریپت مجزا تفکیک شده است که هر یک وظیفه مشخصی در معماری ETL و شبیه‌سازی ایفا می‌کنند:

#### 1. `store_crawler.py` (استخراج ابعاد فروشگاه)
- **منطق اجرایی**: واکشی اطلاعات مکانی و هویتی فروشگاه‌ها با ارسال درخواست‌های `GET` به Endpoint مربوط به `vendors-list` در API اسنپ‌اکسپرس.
- **جزئیات فنی**: 
  - پیاده‌سازی مکانیزم Pagination پویا با استفاده از پارامترهای `page` و `page_size` برای استخراج متوالی تمامی فروشگاه‌های در دسترس.
  - مدیریت Exceptionها و توقف خودکار حلقه (Break) در صورت اتمام داده‌ها یا دریافت خطاهای HTTP.
  - استخراج و نگاشت متغیرهای کلیدی: `storeId`، `storeName`، `lat` و `lon`.
  - حذف رکوردهای تکراری (Deduplication) بر اساس `storeId` پیش از ساخت DataFrame نهایی.

#### 2. `product_crawler.py` (استخراج ابعاد محصول)
- **منطق اجرایی**: استخراج کاتالوگ محصولات فعال از طریق ارسال درخواست `GET` به Endpoint جستجوی محصولات (`express-search/v1/pb/products`).
- **جزئیات فنی**:
  - پیمایش تودرتو روی دسته‌بندی‌های هدف (نظیر `kalabarg`, `beverages`, `junk-food`, `fruits-vegetables`) و مدیریت Pagination مجزا برای هر دسته‌بندی.
  - یکپارچه‌سازی محصولات برای تمامی فروشگاه‌ها (مطابق با فرض ساده‌سازی صورت مسئله؛ تخصیص یکپارچه کاتالوگ به شبکه فروشگاه‌ها).
  - استخراج متغیرهای `productId`، `title` (نام محصول) و `price` (قیمت با اعمال تخفیف). 
  - اجرای عملیات Data Cleaning: حذف رکوردهای فاقد شناسه یا قیمت و Cast کردن ستون قیمت به فرمت عددی یکپارچه.

#### 3. `EX01.py` (شبیه‌سازی برداری تراکنش‌ها و اجرای پایپ‌لاین)
- **منطق اجرایی**: یکپارچه‌سازی ابعاد تولید شده در مراحل قبل و ایجاد ۵۰۰,۰۰۰ تراکنش سنتزی (Synthetic Transactions) با توزیع زمانی ۶۰ روزه.
- **جزئیات فنی (بهینه‌سازی پردازشی)**:
  - **Vectorized Simulation**: برای جلوگیری از سربار فاجعه‌بار محاسباتی ناشی از حلقه‌های تو در تو و استفاده از متد `pandas.sample()`، کل فرایند شبیه‌سازی با استفاده از عملیات ماتریسی و برداری `numpy.random` بازنویسی شده است. این معماری پیچیدگی زمانی $O(N^2)$ را حذف می‌کند.
  - تخصیص شناسه مشتری تصادفی (از یک استخر ۵۰,۰۰۰ تایی) و انتخاب تصادفی فروشگاه با استفاده از ایندکس‌های آرایه‌ای (Array Indexing).
  - تولید بردار زمانی (Time Vectors) با توزیع یکنواخت در بازه ۶۰ روز گذشته و فرمت‌بندی استاندارد `ISO 8601` (`%Y-%m-%d %H:%M:%S`).
  - تخصیص تصادفی ۱ تا ۱۰ قلم کالا برای هر فاکتور، تولید آرایه‌های متناظر `quantity`، و محاسبه ماتریسی `lineAmount = price * quantity`.
  - استفاده از متد `groupby` در Pandas برای تجمیع مبالغ ردیف‌ها و محاسبه `total_paid` در جدول هدر فاکتورها.
  - اجرای فرایند Serialization و ذخیره‌سازی داده‌ها در فرمت CSV با انکودینگ `utf-8-sig` جهت حفظ یکپارچگی کاراکترهای زبان فارسی.

### خروجی‌های ساختاریافته (OLTP Database Schema)
اجرای موفق پایپ‌لاین، ۴ فایل با ساختار دیتابیس رابطه‌ای تولید می‌کند که خوراک خام انبار داده (Data Warehouse) در جلسات آتی خواهند بود:
1. `dim_stores.csv`: حاوی اطلاعات فروشگاه‌های استخراج شده.
2. `dim_products.csv`: حاوی کاتالوگ محصولات متمایز.
3. `fact_tickets.csv`: جدول هدر تراکنش‌ها (Ticket ID, Customer ID, Store ID, Datetime, Num Products, Total Paid).
4. `fact_ticket_items.csv`: جدول سطح اقلام (Line Items) که از طریق `ticketId` به فاکتور متصل است و حاوی جزئیات خرید (Product ID, Quantity, Price, Line Amount) می‌باشد.

## تمرین دوم: پیاده‌سازی انبار داده (Star Schema & ETL)

### شرح پروژه
در این تمرین، داده‌های خام استخراج‌شده از فاز اول به یک انبار داده تحلیلی مبتنی بر طرح ستاره‌ای (Star Schema) تبدیل شده‌اند. هدف، ایجاد بستری بهینه برای تحلیل‌های چندبُعدی و گزارش‌گیری‌های کسب‌وکاری با استفاده از فرآیندهای ETL کامل (بارگذاری اولیه و افزایشی) است. طراحی به‌گونه‌ای انجام شده که تغییرات در داده‌های منبع (مانند بروزرسانی قیمت یا نام فروشگاه) با استفاده از تکنیک‌های SCD ردیابی شده و از ورود داده‌های تکراری جلوگیری می‌شود.

### پیش‌نیازها
- **Python 3.9+**
- پایگاه داده **PostgreSQL**
- بسته‌های پایتون مورد نیاز (نصب با `pip`):
  ```
  pandas numpy sqlalchemy psycopg2-binary
  ```
- متغیر محیطی `DW_DB_URL` شامل رشته اتصال به پایگاه داده، نمونه:
  ```bash
  export DW_DB_URL="postgresql://user:password@localhost:5432/dw_phase2"
  ```

### ساختار فایل‌ها و مسئولیت‌ها

| فایل                   | شرح وظیفه                                                                 |
|------------------------|---------------------------------------------------------------------------|
| `01_create_tables.sql` | ایجاد کلیه جداول، شاخص‌ها، جدول کنترلی و نشان اولیه (Watermark)            |
| `02_initial_etl.py`    | بارگذاری کامل اولیه از چهار فایل CSV و درج در جداول انبار داده            |
| `03_incremental_etl.py`| بارگذاری افزایشی با تشخیص رکوردهای جدید، مدیریت SCD نوع ۲ و به‌روزرسانی نشان |
| `04_sample_queries.sql`| سه کوئری تحلیلی نمونه برای نمایش کارایی طرح ستاره‌ای                      |
| `ANALYSIS_AND_DESIGN.md`| گزارش تحلیلی و مستندات طراحی (فارسی)                                      |

### ترتیب اجرا

1. **ایجاد پایگاه داده و ساخت جداول**  
   یک پایگاه داده PostgreSQL (مثلاً `dw_phase2`) ایجاد کرده و سپس فایل `01_create_tables.sql` را اجرا کنید:
   ```bash
   psql -d dw_phase2 -f 01_create_tables.sql
   ```

2. **اجرای بارگذاری اولیه (Full Load)**  
   اطمینان حاصل کنید که چهار فایل CSV فاز اول (`dim_stores.csv`، `dim_products.csv`، `fact_tickets.csv`، `fact_ticket_items.csv`) در مسیر جاری قرار دارند، سپس:
   ```bash
   python 02_initial_etl.py
   ```
   این اسکریپت تمام ابعاد و جدول واقعیت را با داده‌های اولیه پر می‌کند.

3. **اجرای بارگذاری افزایشی (Incremental Load)**  
   برای شبیه‌سازی دریافت داده‌های جدید یا اجرای دوره‌ای:
   ```bash
   python 03_incremental_etl.py
   ```
   این اسکریپت بر اساس نشان (Watermark) ذخیره‌شده در `etl_control`، تنها رکوردهای جدیدتر از آخرین بارگذاری را پردازش کرده و تغییرات ابعاد را مطابق با قواعد SCD نوع ۲ اعمال می‌کند.

4. **اجرای کوئری‌های تحلیلی**  
   ```bash
   psql -d dw_phase2 -f 04_sample_queries.sql
   ```
   خروجی این کوئری‌ها نمونه‌ای از قدرت تحلیل چندبُعدی فراهم‌شده را نشان می‌دهد.

### تصمیمات کلیدی در طراحی

- **طرح ستاره‌ای** با یک جدول واقعیت مرکزی `fact_sales` که دانه‌بندی آن یک ردیف اقلام سفارش است.
- استفاده از **کلید‌های جایگزین (Surrogate Keys)** برای تمام ابعاد و حفظ کلیدهای طبیعی به‌عنوان شناسه‌های کسب‌وکاری.
- بعد تاریخ (`dim_date`) با کلید عددی `date_sk` به فرمت YYYYMMDD و بعد زمان (`dim_time`) با کلید `time_sk` به فرمت HHMM پیاده‌سازی شده‌اند.
- برای `dim_store` و `dim_product` از **SCD نوع ۲** استفاده شده است؛ تاریخچه تغییرات با ستون‌های `valid_from`، `valid_to` و `is_current` ردیابی می‌شود.
- بعد مشتری (`dim_customer`) به روش **SCD نوع ۱** (درج ساده / به‌روزرسانی بدون تاریخچه) مدیریت می‌شود.
- **جدول کنترلی `etl_control`** آخرین مقدار `datetime` پردازش‌شده را ذخیره می‌کند تا بارگذاری افزایشی تنها رکوردهای جدید را انتخاب کند.
- **جلوگیری از رکوردهای تکراری** از طریق شاخص یکتا روی `fact_sales.ticket_item_id` و عبارت `ON CONFLICT DO NOTHING`.
- **مقاومت در برابر خطا**: در صورت مواجهه با ابعاد گمشده، ردیف‌های مشکل‌دار ثبت و حذف می‌شوند؛ مقادیر جدید تاریخ و زمان در حین ETL افزایشی به‌صورت پویا به ابعاد اضافه می‌شوند.

### لاگ‌گیری و نظارت
هر دو اسکریپت ETL از ماژول `logging` پایتون برای گزارش پیشرفت، زمان اجرای هر مرحله و خطاهای احتمالی استفاده می‌کنند. سطح جزئیات لاگ با تغییر تنظیمات در اسکریپت قابل افزایش است.

### نکات تکمیلی
- در یک محیط عملیاتی واقعی، فایل‌های CSV با جریان داده زنده جایگزین می‌شوند.
- اسکریپت افزایشی فرض می‌کند که چهار فایل CSV نمایانگر آخرین وضعیت فروشگاه‌ها، محصولات و تراکنش‌ها هستند؛ با مقایسه با محتوای فعلی ابعاد، تغییرات را تشخیص می‌دهد.
- تمامی عملیات ETL برای درج‌های دسته‌ای و به‌روزرسانی‌های کارآمد از هسته SQLAlchemy استفاده می‌کنند.

### بهینه‌سازی‌های عملکردی
- **پارتیشن‌بندی و درج موازی**: جدول واقعیت با استفاده از `ThreadPoolExecutor` و تقسیم داده‌ها به تکه‌های ۵,۰۰۰ ردیفی با قابلیت `ON CONFLICT DO NOTHING` به‌صورت همروند بارگذاری می‌شود (تعداد کارگزاران: ۴).
- **تجزیه برداری تاریخ**: برای جلوگیری از گلوگاه پردازشی روی ۲.۷ میلیون رکورد، تبدیل رشته‌های زمانی با تابع برداری `pd.to_datetime(…, errors='coerce')` انجام می‌شود.
- **کاهش عملیات تک‌به‌تک**: حلقه‌های `iterrows()` با عملیات برداری یا درج دسته‌ای جایگزین شده‌اند تا سرعت اجرا در حجم داده‌های بزرگ تضمین شود.
